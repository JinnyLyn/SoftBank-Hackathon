# 제품 방향 — 관리형 배포와 사용자 독립 도메인

기준 ID: `2026-10-10-managed-domains-v1`

상태: **제품 방향은 팀 확정 / 이번 도메인 시연 범위는 확인 필요**. [10/10 오프라인 미팅](https://app.notion.com/p/3f58bee9ada480188daecffb30cd7e1b) 하단의 서비스 방향 제안에 대해, 2026-10-10 진서의 문서 갱신 요청에서 “팀 확정 — 새 개발 기준으로 반영”을 확인했다. 이후 같은 요청에서 **백엔드~프런트 목록은 구현 시 필요한 것으로 제안한 내용**이며, 기존 확보 도메인 시연과 신규 구매 자동화 중 실제 진행 범위를 검증해야 한다고 정정했다. 회의록 제목이나 목록만으로 세부 작업 전체를 확정하지 않는다.

이 문서는 제품 방향의 단일 기준이다. 실행 절차는 [WORKFLOW](../WORKFLOW.md), 공통 개발 지침은 [AGENTS](../AGENTS.md), 구현된 API는 [back/API](../back/API.md)를 따른다. 과거 회의 기록·MOCK·기존 화면이 아래 결정을 되돌리는 근거가 되지 않는다. 방향 확정은 기능 완성이나 실제 AWS 변경·도메인 구매 승인을 뜻하지 않는다.

## 1. 확정된 제품 경계

- 대상은 클라우드를 모르는 비전공자·예비 창업자다. AWS 계정·IAM 키·리전·DNS 설정 지식이 이미 있다고 가정하지 않는다.
- 운영자가 AWS 계정과 기반 인프라를 준비하고, 플랫폼이 그 위에 사용자 앱을 배포한다. 사용자 AWS 계정 연결은 기본 가입·배포 흐름의 전제조건이 아니다.
- 사용자는 소스, 사용 규모·예산, 원하는 독립 도메인을 선택하고 비용을 승인한다. 신규 등록을 지원할 경우 필요한 등록 정보·본인 확인도 받는다. 이미 등록된 이름의 사용 권한이나 도메인 가용성 조건을 생략할 수는 없다.
- 플랫폼은 지원 범위 안에서 인프라 준비, 앱 배포, 독립 도메인 연결, DNS·HTTPS, 최종 접속 확인을 담당하는 것을 목표로 한다. **신규 도메인 구매 자동화를 이번 해커톤의 필수 구현으로 확정한 것은 아니다.** IAM·DNS 수동 안내만 제공한 것을 자동화 완료로 보지 않는다.
- 사용자 독립 도메인 전체를 연결한다. 운영자 AWS를 쓴다고 사용자에게 `앱이름.플랫폼도메인`을 강제하지 않는다. 임시 주소는 미리보기일 뿐, 선택한 독립 도메인의 연결 완료를 대신하지 않는다.
- 도메인의 등록인, 갱신·해지 선택, 관리·이전 경로는 사용자 권리를 보장해야 한다. 운영자 명의의 도메인을 사용자 소유라고 설명하지 않는다.
- 제품 배포 대상은 **AWS만**이다. 로컬 Docker Compose는 개발·검증용이며 온프레미스 상품화·다중 클라우드는 현재 범위 밖이다.
- 승인된 계획만 실행하고, 첫 배포 실패에는 롤백을 제공하지 않는다. 이후 실패의 롤백도 사용자가 새 계획을 확인·승인해야 한다. 자동 롤백·무제한 AI 수정은 활성화하지 않는다.

## 2. 이번 시연 범위와 완료 조건

두 경로를 구분한다. 현재 확인한 저장소와 회의 기록만으로 어느 경로를 이번 시연으로 최종 선택했는지는 확정할 수 없다. 담당자는 선택한 경로·수동 사전 준비·검증 증빙을 연결 PR과 [남은 결정](OPEN_QUESTIONS.md)에 기록한다. 이를 기다리느라 기존 앱 배포·분석 등 독립 작업을 멈추지는 않는다.

| 경로 | 필요한 증빙 | 그 결과로 말할 수 없는 것 |
|---|---|---|
| A. 미리 확보한 독립 도메인으로 연결·배포 시연 | 도메인 사용 권한, 사전 준비와 자동 처리의 구분, DNS·인증서·앱 라우팅, 해당 주소의 유효한 HTTPS와 앱 응답 | 신규 구매 자동화, 임의의 신규 사용자가 준비 없이 끝까지 배포할 수 있음 |
| B. 신규 사용자의 도메인 구매부터 자동화 | 가용성·실제 가격 조회, 등록인 정보·동의·비용 승인, 등록 작업 결과, DNS·인증서·라우팅, 최종 HTTPS, 실패/재시도 시 중복 구매 방지 | 화면이나 MOCK만으로 실제 구매·연결 성공, 모든 DNS 업체 지원 |

제품의 목표 흐름은 앱 제출·사용 규모 입력 → 독립 도메인 선택 → 구성·비용 확인 → 승인 → 배포·연결 → HTTPS 접속 확인이다. A에서는 미리 준비한 도메인을 사용했다는 제한을 밝힌다. 사용자가 임의의 독립 도메인을 선택하는 전체 제품 요구를 충족했다고 확대하지 않는다. B의 등록인·구매·갱신 처리는 B를 맡기로 정한 경우에 추가한다.

- “나중에”를 제공한다면 미리보기로 명확히 표시한다. 독립 도메인 선택권을 없애거나 도메인 연결까지 성공했다고 표시하지 않는다.
- 비용 화면은 호스팅 요금/추정치와 제외 항목을 구분한다. 구매를 지원하면 최초 등록비와 갱신 비용·주기도 구분한다. 공유 인프라 원가를 모든 사용자에게 그대로 청구하는 것으로 가정하지 않는다. 과금 방식은 [남은 결정](OPEN_QUESTIONS.md)에서 확정한다.
- 유료 도메인 등록·추가 자원 생성은 해당 비용 승인 이후다. 권한 연결 동의와 비용 지출 승인을 같은 것으로 처리하지 않는다. 승인 이후 가격·도메인·설정이 바뀌면 새 승인 기준을 만든다.
- 기존 도메인은 제어 권한을 검증한다. 자동 설정을 지원하는 DNS 업체와 사용자 인증·위임 방법을 명시한다. 모든 업체의 도메인을 권한 없이 자동 연결할 수 있다고 약속하지 않는다.
- 도메인 등록, DNS 전파, 인증서 발급은 비동기다. 앱의 `healthy`와 도메인의 연결 상태를 분리하고, 실패·대기·사용자 조치 필요·재시도 조건을 표시한다.
- 최종 성공은 사용자가 선택한 호스트 이름으로 유효한 HTTPS 접속과 해당 앱 응답을 확인한 뒤 표시한다. ALB 기본 주소 접속이나 자체 서명 인증서 시험으로 대체하지 않는다.

## 3. 파트별 구현 후보 — 확정 작업 목록이 아님

아래는 회의록의 제안을 정리한 설계 후보다. **일괄 구현 지시·새 담당 배정·확정 API가 아니다.** 먼저 A/B 시연 범위와 실제 자동화 경계를 확인하고 필요한 부분만 작업으로 확정한다. 필드·endpoint·상태 enum은 백엔드·프런트·인프라 담당자가 같은 PR 또는 연결된 PR로 맞춘다. 이미 있는 프런트의 제안 API를 백엔드 확정 계약으로 간주하거나 기존 앱 배포 API를 호환성 없이 삭제하지 않는다.

### 백엔드

- 프로젝트와 사용자 소유 관계를 확인할 수 있는 도메인 자원, 등록인 정보 참조, 승인/동의 기록, 등록 작업 ID, 인증서·검증 레코드·갱신 정보를 관리한다.
- `domains` 테이블과 가용성 조회·등록 요청·기존 도메인 연결·상태 조회 API는 제안이다. A에 필요한 연결 상태와 B에만 필요한 등록·구매 정보를 나눠 계약을 정한다. 실제 migration·OpenAPI가 생기기 전에는 구현된 API 목록에 넣지 않는다.
- 중복 등록·중복 결제를 막는 요청 식별자, 도메인 중복 할당 방지, 소유권 검증, 실패 후 재개를 계약에 포함한다. AWS 작업이 완료됐는데 응답만 유실된 경우도 재구매하지 않게 한다.
- 등록인 개인정보·동의 증빙은 별도 접근 통제 아래 보관한다. 일반 로그·LLM 입력·Terraform 변수/plan/state에 등록인 원문을 넣지 않는다.

### worker / deploy.sh / Terraform

- 기존 빌드·저장 plan 승인·apply·헬스체크 흐름을 유지하면서, 승인된 도메인 등록/연결 작업과 인증서 요청 → DNS 검증 → ALB 호스트 규칙 → 최종 접속 확인을 연결한다.
- 공유 443 리스너와 앱별 호스트 규칙은 제안된 연결 방식이다. 채택할 경우 리스너·규칙·DNS·인증서의 관리 주체와 state 경계를 정하고, 이미 수동 생성한 리소스는 소유권·기존 state를 확인한 뒤 관리 체계에 편입한다. 문서만 보고 진행 중 포트 리스너를 즉시 제거하지 않는다.
- 포트별 리스너 제약이 줄어도 앱 수가 무제한이 되지는 않는다. ALB 규칙·대상 그룹·인증서·보안 그룹 등 실제 계정의 할당량을 확인한다.
- 앱 삭제와 도메인 등록 해지·갱신 중단·DB 삭제는 별도 동작이다. 앱 소유 연결 규칙만 정리하고, 공유 인증서·hosted zone·다른 앱 레코드를 삭제하지 않는다. 인증서는 참조·소유권을 확인하고, 독립 도메인 등록을 일반 `destroy`에 묶지 않는다.
- 운영자의 계정 이전은 [운영자 AWS 문서](OPERATOR_AWS.md)를 따른다. `AWS_PROFILE` 변경만으로 기존 state·ECR·기반 출력·저장 plan이 새 계정으로 이전됐다고 간주하지 않는다.

### 프런트 / LLM

- 사용자 AWS 연결을 필수로 요구하는 기존 `QuickConnect` 흐름을 관리형 배포 흐름으로 전환한다. 운영 환경의 준비 상태와 사용자 도메인 입력을 구분한다.
- 선택한 구현 범위에 맞는 도메인 입력·비용·승인·DNS/인증서 상태를 보여준다. 구매 미지원이면 실제 구매 가능처럼 표시하지 않는다. 기존 도메인의 DNS 수동 입력 안내를 제공하는 단계라면 아직 지식 부담이 남아 있음을 밝힌다.
- LLM은 코드 분석·허용된 설정 제안·실패 설명을 맡는다. 계정·도메인 소유권, 가격, 구매 승인, DNS 변경 권한을 LLM 추측으로 결정하지 않는다.

**검증 결론:** 기존 도메인 연결을 준비하는 기록과 두 경로의 프런트 시제품은 있다. 신규 구매 자동화의 실구현·통합 성공 근거는 없으며, A도 최신 실제 접속·자동화 증빙은 추가 확인이 필요하다. 담당자가 선택 경로, 코드 SHA, 시험 주소·확인 시각, 수동 사전 준비, 실제/MOCK 결과를 남겨야 이번 시연 범위와 완료 여부를 확정할 수 있다. 공개 주소 접속만으로 구매 과정이나 사용자 소유권까지 검증했다고 하지 않는다.

발표자 PC의 데모와 다중 사용자 공개 서비스도 구분한다. 공개 서비스 전에 사용자 인증·프로젝트/도메인 소유권·작업 격리·운영 과금 경계를 구현·검증해야 한다.

## 5. 진행 중 에이전트에 적용

[WORKFLOW §3.1](../WORKFLOW.md#31-개발-기준-변경을-진행-중-작업에-반영)에 따라 기준 ID와 확인한 main SHA를 작업 요약·PR 보고에 남긴다. 기존 미커밋 변경을 버리지 않으며, 타인 브랜치를 대신 수정하거나 진행 중 세션을 자동 종료하지 않는다. 문서가 main에 합쳐져도 이미 실행 중인 에이전트가 자동으로 다시 읽었다고 가정하지 않는다.
