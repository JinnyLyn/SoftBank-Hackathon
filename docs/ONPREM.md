# 이 PC의 Docker에 배포하기

최신 main의 로컬 배포 엔진을 별도 서비스로 연결한 경로다. **AWS 기본 화면(`/`)과 AWS 실행 설정은 변경하지 않는다.** 이 문서는 현재 사용자 요청의 범위이며 과거 AWS-only 제품 방향 문서를 전체 변경하는 팀 결정이 아니다.

## 실행

Windows 11에서는 Docker Desktop의 WSL 통합을 켜고 WSL 터미널에서 실행한다. Linux Docker도 같은 명령을 사용한다. Docker Engine/Compose, `uv`의 Python 3.12, Node 22.12 이상이 필요하다. 실행기는 도구를 자동 설치하지 않는다.

```sh
# 최초 한 번, lockfile대로 프런트 의존성 준비
npm ci --prefix front
# 필요하면 Python 3.12 준비: uv python install 3.12
bash scripts/run_onprem.sh
```

- 전용 화면: **http://127.0.0.1:15173/onprem**
- API: `http://127.0.0.1:18000`, 기존 8000/5173 서비스는 변경하지 않는다.
- API·MySQL·규칙 분석기·로컬 배포 worker·웹을 함께 시작한다. MySQL migration도 실행한다.
- 기본 데이터: `~/.local/share/paved-clouds/onprem`. 다른 포트/저장 위치는 `--api-port`, `--web-port`, `--state-dir`로 지정한다. 저장소 밖의 전용 경로를 사용한다.
- `Ctrl-C`: 이 실행기의 서비스만 종료한다. **DB 볼륨, 업로드, 계획, 이미 배포한 앱은 보존**한다. 같은 데이터 경로로 다시 시작하면 API에서 기존 프로젝트·배포 기록을 조회할 수 있다. 화면의 진행 중 입력은 새로고침 시 초기화된다.

현재 Docker endpoint를 실행 시작 때 고정하며 SSH/TCP 원격 context는 자원을 만들기 전에 거부한다. 전역 Docker context나 기존 `.env`는 수정하지 않는다. `ai/.env`를 읽지 않고 `--no-llm`을 사용한다. AWS/유료 LLM 키는 이 경로에 필요하지 않다.

## 배포

1. 준비 상태에서 API·DB·Docker·분석기·worker가 모두 준비됨인지 확인한다.
2. ZIP 파일 또는 공개 GitHub 저장소를 선택하고 소스만 입력한다. GitHub는 저장소 URL과 브랜치(기본 `main`)를 입력한다. Dockerfile을 포함하되 비밀값·`.env`·가상환경·node_modules는 제외한다.
3. 규칙 분석과 로컬 계획을 기다린다. Dockerfile 초안만 있거나 지원 불가면 안내에 따라 소스를 수정하여 다시 제출한다.
4. Compose·실행 변수·금액 제외 항목·fingerprint를 검토하고 명시적으로 승인한다. 검토한 계획이 바뀌면 재검토해야 한다.
5. 빌드·DB 초기화·앱 HTTP 헬스 확인 후 주소를 연다. **플랫폼을 실행하는 PC의 Docker**에 배포한다. 브라우저 방문자의 PC나 원격 서버가 아니다.

기존 `sample-back/`와 `sample-front/`를 폴더 구조 그대로 하나의 ZIP에 넣으면 실제 샘플로 검사할 수 있다. 샘플 Dockerfile은 저장소 루트 기준 `COPY sample-back ...`를 사용하므로 폴더를 평탄화하지 않는다.

월 예산·예상 사용자·접속 패턴·앱 설명은 입력받지 않는다. 공통 API에는 로컬 기본값(`~100`, `steady`, 예산 `0`, 용도 없음)을 전달하며, worker는 ‘작게 시작’ 구성과 실제 Docker CPU·메모리 한도로 계획을 계산한다. 승인 전에 실제 자원 한도를 확인한다. 로컬 추가 호스팅 금액이 0이 아닌 계획은 승인하지 않는다. 기존 AWS 입력·추천 흐름은 변경하지 않는다.

HTTPS·독립 도메인·SSH 원격 배포·자동 재배포·로컬 롤백은 제공하지 않는다. `localhost`는 공개 주소가 아니다. 클라우드 추가 요금 추정이 0이어도 PC·전기·네트워크 비용은 별도다. 실제 앱의 기능·데이터 검증은 HTTP 헬스 확인과 구분한다.

## 준비가 안 되었을 때

`GET /api/onprem/readiness`는 API/DB를 직접 확인하고, 실행기가 기록한 Docker 검사·소유 프로세스 상태·실제 API 성공 관측을 함께 읽는다. 기존 `/health`, `/ready` 의미는 그대로다. 설정 없는 기존 API는 `unconfigured`이다.

- 시작 중: 첫 검사나 프로세스 시작을 기다리는 중이다.
- 중단: 해당 프로세스 종료, DB 연결 또는 Docker 검사 실패다.
- 상태 만료: 실행기 관측이 15초 이상 오래되었거나 run-id/형식이 맞지 않는다.
- 분석·빌드 중: 실제 단계 시작에 설정한 제한 시간 안에서만 준비로 표시한다. 단순 heartbeat가 기한을 연장하지 않는다. 이 관측 기한은 작업 취소·재시도 정책이 아니다.
- API 연결 실패: 실행 터미널/포트와 데이터 경로의 `logs/`를 확인한다. 사용 중 포트를 강제로 비우지 않는다.

준비가 안 되면 새 분석·승인을 막되 현재 입력/검토와 이미 등록한 배포의 상태 조회를 유지한다. 준비가 복구되어도 자동 승인하지 않는다. 작업자 종료 시 이미 승인된 작업이 취소되거나 자동 재시도되는 것은 아니다. 실패는 로그를 확인하고 새 계획을 검토한다.

데이터 경로의 `run.json`에는 해당 실행의 project/endpoint/프로세스 ID가 있다. 정리는 이 소유 범위를 확인한 뒤 수행한다. `docker system prune`이나 다른 프로젝트의 `down`을 사용하지 않는다. 데이터·배포 앱의 영구 삭제는 서비스 종료와 별도 작업이다.
